# dmx — Playground and Release

Part of the [dmx specification](SPEC.md).

## [playground] Browser Playground

The project website MUST expose the production string pipeline as an interactive browser playground. Generation happens locally in WebAssembly: source MUST NOT be uploaded or evaluated by a remote service.

### [playground.wasm] Generator Boundary

The WASM exports MUST call the same validated, byte-exact pipeline as `dmx build`, with region insertion enabled. The custom-template export MUST accept the Dart source and exact Mustache template, infer one unambiguous registered macro, and render that template against the macro's production Rust context. Each result is a two-element `[success, sourceOrDiagnostic]` value so invalid Dart, an invalid template, or an ambiguous context remains a typed UI state rather than becoming a JavaScript exception. An unchanged successful input returns the input itself.

The website build MUST execute the compiled artifact over a valid golden source, its generated/idempotent form, invalid Dart, every displayed source/template pair, and an edited template before bundling it. Generated WASM glue is a build artifact and MUST NOT be committed.

### [playground.interface] Interaction

The playground lives on its own dedicated page, not embedded in the marketing page. On desktop viewports the playground MUST fill the browser viewport both horizontally and vertically below the site header, with no page-level scrolling; on narrow viewports the stacked editors may extend the page instead. The playground MUST provide editable Dart and Mustache inputs, visible generated output, representative macro samples, reset/copy actions, compiler status, and an inline diagnostic state. Generation is live: every edit to either input regenerates the output immediately, with no explicit generate action. Generated output taller or wider than its pane MUST scroll within the pane. Both inputs are bounded to protect the synchronous browser pipeline. Controls MUST remain keyboard accessible, and the marketing page MUST remain readable if JavaScript or WASM initialization fails. The Dart input, mixed Dart/Mustache template input, and generated Dart output MUST all provide live, language-aware syntax highlighting. Playwright MUST drive the production site through code edits, template edits, generation, and diagnostic states in a real browser, including a mobile viewport.

#### [playground.interface.inline-mode] Inline Watch Mode

The playground's default presentation mirrors `dmx watch`: there is no separate output pane. Every successful generation splices the regenerated file back into the Dart editor itself, so the generated members appear between the `//#region`/`//#endregion` dividers of the code being edited — the same inline emission the editor extension shows on disk. The caret MUST survive the splice: a selection before the regenerated bytes keeps its offsets, one after them shifts by the length difference, and one inside them collapses to the splice point. A failed generation MUST NOT touch the editor's content; the diagnostic surfaces through the status bar only. The copy action copies the whole inline file.

A visible, keyboard-accessible toggle switches between this inline mode and the split view of [playground.interface], which keeps its separate generated-output pane. Toggling regenerates immediately in the newly selected mode.

### [playground.hosting] Hosting

The site is published to GitHub Pages from the default branch, and the build that publishes it MUST be the same `make website` that CI runs — compiled generator, Node smoke test, type check, bundle, and the Playwright run, in that order, with deployment downstream of all of it. A site whose playground is broken is worse than no site, because it demonstrates the product failing.

The site is served from the root of its own domain, and every asset reference MUST resolve there. A build carrying a path prefix from anywhere the site used to live serves HTML that renders and assets that 404 — a page whose structure is intact and whose every stylesheet is missing.

Nothing may be trusted to notice that by looking at the markup, because the markup is identical either way and a uniformly unstyled site compares equal to itself. Every published page MUST therefore be loaded and every reference it makes proven to resolve, and a stylesheet MUST be proven by the rules it contributes: a link whose href 404s still reports a stylesheet object, an empty one.

The server the suite drives MUST answer a path with no file behind it the way the host does — with a 404. A preview server that falls back to the homepage answers 200 for every asset a broken build asks for, and the whole suite passes against a site that is dark.

## [release] Release

A tag is the release. Everything the release publishes MUST be read from the tagged commit: nothing commits, nothing pushes, and no job checks out a branch. The one edit a release makes to the tree is stamping the version its tag names into its own throwaway checkout [release.version], and that stamp MUST be a pure function of the tagged commit and the tag — reproducible by hand from both, with no other input. A release that edits the tree in any other way is a release nobody can reproduce from the tag it claims to be.

Publishing MUST be gated on a scan of the released commit itself with the current query set, as a hard gate — a release a security finding cannot stop is not gated [GITHUB-CODE-SCANNING]. Where that scan cannot run, it reports as skipped rather than passing, and the gate MUST distinguish the two.

Packaging MUST route through the single recipe that a local `make rebuild-install-vsix` uses, so the bundle installed by hand is the bundle that ships. Every platform bundle MUST be proven to contain a binary before it is published, and the universal bundle proven to contain none; where the runner can execute what it just built, it MUST, and the binary MUST report the version being released.

There MUST be a way to run the entire matrix without publishing. A cross-compile that breaks should be found on a button press, not on a tag that cannot be taken back.

### [release.verification] A tag is proven before it publishes

Publishing MUST be gated on the full functional suite — formatting, lints, the duplication budget, the coverage-enforced test run, the golden corpus, every worked example, and the packaged extension driven in a real editor — run against the tagged commit itself. A release proven only by a version check and a `--version` call is a release nobody tested.

The suite MUST be the same one a pull request has to pass, invoked rather than restated. Two definitions of "green" drift, and the copy that publishes is the one that drifts unwatched.

Passing on the pull request that merged is not this gate. A tag names a commit that nothing has necessarily built: it may sit on a merge whose two green parents disagree, or on any commit a person chose to tag. The gate MUST run where the tag points.

A gate that reports anything other than success MUST block the publish. Only a gate that genuinely cannot run in an environment — the security scan on a private repository — may report as skipped, and the release MUST distinguish "skipped" from "passed" [GITHUB-CODE-SCANNING].

### [release.authentication] Trusted publishing

The Visual Studio Marketplace MUST be published through Microsoft Entra workload identity federation. The publish job runs in the protected `release` environment, requests a GitHub OIDC token with `id-token: write`, exchanges it for a short-lived Azure DevOps access token, and uses that token only for the duration of the job. A stored Marketplace personal access token is forbidden.

The Entra application MUST be a Contributor member of the `nimblesite` Marketplace publisher, and its federated credential MUST trust the release environment's GitHub subject. Source, pull-request, and manually dispatched builds MUST NOT receive a publish identity or publish an artifact.

### [release.version] The tag is the version

Nothing in the tree names a release. Every package file MUST carry a placeholder version, and a release MUST stamp the version its tag names into its own checkout before it builds. Pushing a tag is therefore the whole act of releasing: no version is bumped beforehand, no tag can be refused for a file somebody forgot to edit, and no two files can disagree — there is only one number, and it is on the tag.

The placeholder MUST be a version every consumer of these files accepts, and MUST be one no release can be. A build that nothing stamped reports it, which is the honest answer: an untagged build is not a release.

The version MUST be `major.minor.patch` — the marketplace accepts nothing else, and a tag it will reject MUST be refused before anything is built rather than halfway through a publish.

Structured files MUST be rewritten by a parser for their format, never by pattern substitution, and the tool MUST be exercised by tests that pass it the versions a release would. Each file is owned by the toolchain that owns its format: whichever mechanism a file uses, the version it ends up carrying MUST be the tag's and MUST come from one decision, made once per release.

A file may satisfy this without being rewritten at all where its consumer can take the version by another route — a compile-time input, say. Such a file's placeholder is then permanent, and the release MUST prove the artifact it produced reports the tag's version rather than assume it.

A `--check` mode MUST run in ordinary CI and assert that every package file still carries the placeholder, so a file edited by hand fails on the pull request that did it rather than on a tag. Before a tag publishes, that same check MUST pass, and the release notes for the version being released MUST already exist in each changelog under a heading the release renames — a release whose notes nobody wrote publishes a page that says nothing.

Where a generated file reports a version it reads from a stamped file, the release MUST regenerate it. Publishing a package that reports the release before it is publishing a package that lies about itself, and pub.dev cannot take that back.

`dmx --version` MUST report the version the binary was built at. A binary that ships inside a bundle, and that `dmx.path` can replace, has to be able to say which build it is.
