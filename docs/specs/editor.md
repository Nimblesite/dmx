# dmx — Editor Integration

Part of the [dmx specification](SPEC.md).

## [editor] Editor Integration

A correct `dmx watch` that nobody launches is indistinguishable, from the editor, from a broken one: you delete a generated member and it stays deleted. Generation that runs only when someone remembers to run it is generation nobody trusts, so the editor MUST start it without being asked.

### [editor.extension] The VS Code extension

`src/editors/vscode`, published as one VSIX per platform, each carrying the `dmx` binary for that platform. The consumer installs one extension and has a working watcher: no Rust toolchain, no `cargo install`, no task to allow.

#### [editor.extension.binary] Binary resolution

In order: the `dmx.path` setting, the copy bundled in the VSIX, the workspace's own `target/release/dmx`, its `target/debug/dmx`, the same two under `src/dmx/`, then `dmx` on `PATH`. Working on `dmx` itself therefore picks up the local build with no configuration — which is why `src/dmx/` is searched at all, that being where this repository keeps the crate — and consumers never see the fallback at all.

A VSIX is a zip, and the execute bit does not survive every route from a build machine to an extensions folder. The extension MUST restore it rather than report a binary it shipped as unusable.

#### [editor.extension.autostart] Auto-start

Activation is a workspace containing a `pubspec.yaml` or an open Dart file. On activation, for each workspace folder:

1. What is watched is decided by [editor.extension.paths]. Configured paths that do not exist are skipped. A package with no `lib` yet is not an error, and MUST NOT produce a diagnostic.
2. `dmx build --insert-regions` runs once, then `dmx watch` starts — the same order, and for the same reason, as `make dev`: `watch` refuses `--insert-regions`, so a class annotated while the editor was closed would otherwise never get its divider [cli].
3. A build that fails MUST NOT stop the watcher from starting. The file it choked on is the one being fixed.
4. A watcher that exits MUST surface that it exited and MUST NOT be restarted automatically. A crash loop that hides itself is worse than a stopped watcher that says so.

#### [editor.extension.paths] What a folder is watched at

`lib` is the right answer for one package opened on its own and the wrong answer for every other layout. A repo keeping its packages under `examples/`, `packages/` or `apps/` has no `lib` at its root, and a watcher that only looks there is handed nothing to watch — which is indistinguishable, from inside the editor, from a generator that has stopped working.

- Where `dmx.paths` was set explicitly, that setting is the whole answer: naming paths means naming all of them, filtered to those that exist.
- Left at its default, a workspace folder MUST be watched at its own `lib` **and** at the `lib` of every Dart package below it — a directory holding both a `pubspec.yaml` and a `lib`. The search MUST skip hidden directories, dependency and build output (`node_modules`, `build`, `target`, `.dart_tool`) and the platform folders of a Flutter app, MUST stop descending at a package (a package's `example/` is generated by watching the package), and MUST be depth-bounded so opening a large tree costs a handful of directory reads.
- Each watched path is passed to one `dmx watch` invocation; per-package worker discovery is [dartmacros.discovery]'s business, not the extension's.

#### [editor.extension.refresh] The buffer follows the file

Generation the editor does not show has not happened, as far as the person looking at it is concerned. dmx writes through an atomic rename [execution.store], so the destination briefly does not exist, and an editor's own file watcher is entitled to miss that — which leaves a buffer showing members the file no longer has while the bytes on disk are correct. It is worse than cosmetic: editing that stale buffer makes the next save a conflict the editor refuses.

Reloading a document from disk is the editor's own responsibility and MUST be left to it. The extension MUST NOT write the file's bytes back into an open buffer to force the refresh: reading the file outside the editor's file service and applying it as a workspace edit leaves the editor holding the version stamp it recorded *before* the rename, so the save that follows is refused as `File Modified Since` — manufacturing the very conflict this section exists to prevent, and leaving the model in a state where every later save fails too.

A buffer with unsaved changes MUST NOT be reverted: discarding a user's edits is a worse failure than the staleness.

#### [editor.extension.bundle] What the bundle contains

The manifest is a set of promises about files — an entry point, an icon, a grammar per declared scope, a command per palette entry — and every one of them MUST exist and MUST survive `.vscodeignore` into the VSIX. None of that fails at build time: it fails as a broken listing or as a command that reports "command not found" to whoever ran it, so it MUST be asserted before packaging.

One VSIX is published per platform, each carrying exactly one binary. A universal VSIX carrying NO binary MUST also be published: it is what the marketplace serves to a platform with no build of its own, where resolution falls through to `PATH` [editor.extension.binary]. Without it, an unmatched platform cannot install the extension at all.

dmx runs a binary over the folder that is open, and `dmx.path` can name one inside it. The extension MUST therefore decline to run in a folder the user has not trusted.

#### [editor.extension.e2e] The artifact, driven

A bundle asserted file-by-file can still be a bundle that does not work; the only proof is the packaged VSIX doing its job in a real editor. The e2e suite MUST therefore drive the artifact itself: the extension unpacked from the packaged VSIX, running the engine binary that VSIX carries — rebuilt from the same tree in the same invocation — inside a real VS Code, over a real Dart workspace. Driving the extension's source tree instead of the unpacked artifact would let `.vscodeignore` eat the bundle without a test going red.

Every scenario is exercised through user actions — opening the folder, typing, saving, running a palette command — and asserted where a user sees the effect: the editor buffer and the disk. Normatively, the suite MUST prove:

1. Opening the workspace inserts regions into annotated classes that have none and generates every member, with no command run [editor.extension.autostart].
2. An edit saved in the editor regenerates that file's region — growing, renaming, and deleting a field each land in every generated member — and the editor picks the regenerated bytes up without any command.
3. A file that stops parsing is refused alone: its bytes survive untouched, its neighbours keep regenerating, and fixing it resumes generation [engine.api].
4. The palette commands are live: after `dmx.stopWatcher`, `dmx.build` inserts regions for classes created while nothing watched; after `dmx.restartWatcher`, a plain save regenerates again.
5. With the bundled binary's execute bit stripped before launch — the zip route's failure mode — generation still runs, proving the extension restores it [editor.extension.binary].

#### [editor.template-highlighting] Template highlighting

A dmx template is Dart with Mustache tags in it, and is highlighted as both. The `.mustache` grammar includes the installed Dart grammar, so Dart stays correct as Dart does; the tags arrive as an injection at `L:` priority, which is what lets a tag be a tag inside a Dart string literal — `'{{className}}.{{name}}'` — where templates put them constantly. With no Dart grammar installed the tags MUST still highlight.

### [editor.dart-highlighting] Dart highlighting

Two things in a Dart source file are dmx's and cannot be known to the Dart grammar, so dmx MUST contribute them as an injection over `source.dart`:

1. **The divider it owns.** An unlabelled `//#region` / `//#endregion` pair MUST read as a divider rather than as one more comment, so the boundary between the author's bytes and the generator's is visible without counting braces. A *labelled* fold is the author's own and dmx never writes into one [emission.inline-backend.region-location], so it MUST NOT be highlighted as dmx's. A marker that does not own its line is not a divider.
2. **Its annotations,** in two tiers scoped apart: the ones that cause a region to be written at all, and the ones that configure what gets written. Dart's own annotations MUST be left to Dart — an extension that repainted `@override` would be claiming a tool put it there that did not.

The injection MUST NOT depend on a Dart grammar being installed, and MUST NOT claim an annotation name written inside a string literal.

The example and the golden corpus between them use every annotation dmx ships, which makes them the drift gate: an annotation either of them uses that this grammar does not know MUST fail the suite. A macro added without teaching the grammar about it reads as plain code, and the author only finds out by squinting.
